# Zune 30G 持久中文显示教程

## 1. 本教程解决什么问题

目标是让原生“音乐”中的中文歌名在真实重启后仍能显示。
它不翻译整个菜单，也不把第一代 30G 的方案套用到 Zune HD。

第一台测试机已经完成原生中文显示和重启确认；第二台适配版的最终屏幕与声音验证尚待完成。
请先阅读 [功能与验证范围](../features.md)。

本版公开了原理、加载器、离线注册表工具和验证步骤。**没有提供通用 NK 镜像、
一键刷机工具或可直接套用的启动器/安全区补丁。** 第 6 节涉及的固件封装与接受策略，
需要结合具体机器另行核对；不能把中间文件改名为 `nk.bin` 后直接安装。

## 2. 准备资料与恢复路径

- 确认设备确实是一代 Zune 30G，以及固件、启动器和已有改动的实际状态。
- 私下保存该机原始系统、启动相关数据和唯一安全数据；记录大小与哈希。
- 在修改系统前确认这台机器的恢复入口、电脑识别及原版系统写回流程。
- 恢复画面能出现不等于完整恢复已经验证。
- 不使用另一台机器的完整闪存、安全区或含身份数据的 NK 作为通用恢复包。

这些要求来自本项目曾经实际遇到的黑屏与认证兼容问题。

## 3. 准备字库

历史验证字库的设备路径和字族为：

```text
\Hard Disk\Fonts\ZuneCJK_UI_20261027.ttf
字族：Zune UI CJK
文件大小：8206424 字节
```

该历史字库合并了原界面字形和中文字符，未随仓库分发。
可以自行准备有相应使用权的字体，但必须检查字族名称、字符覆盖、文件大小和实际渲染。
换用字体后，不应继续沿用原字库的“已验证”结论。

```powershell
python -m pip install -r requirements.txt
python tools/inspect_font.py local-inputs/MyFont.ttf
```

检查输出的 `families`、`bytes`、`sample_coverage` 和 `coverage`。
当前历史字库的基本汉字映射为 20,909 个，有日文假名映射，但韩文音节映射为 0。
字符映射存在只表示字体里有字，不能单独证明原生音乐界面已经正常显示。

## 4. 字体加载器

`artifacts/ZCJKBoot.exe` 是历史成功方案的原生 ARM CE 加载器，不需要启动 XNA 游戏。
它检查固定路径与文件大小，调用 `AddFontResourceW`，然后通知 `Init` 继续启动。

预编译版本只接受 8,206,424 字节的字库。它的大小检查不是数字签名或完整哈希验证。
若字体不同，需用自己的 3.30 固件提取 `coredll.dll`，在电脑上重建：

```powershell
python tools/build_font_loader.py --coredll local-inputs/coredll.dll --font-size 8206424 --output generated/ZCJKBoot.exe
```

将示例大小替换成自己字体的实际大小。构建工具只在电脑上生成文件，不会安装到设备。
`coredll.dll` 不要提交到仓库。加载器输出必须随后经过提取检查和实际启动验证。

## 5. 配置字体链接和启动顺序

以下是已验证的启动关系：

```text
Launch20 = device.exe
Launch30 = gwes.exe          Depend30 = 20
Launch45 = \Hard Disk\Fonts\ZCJKBoot.exe
                             Depend45 = 30
Launch60 = services.exe      Depend60 = 20,45
```

对应字体链接：

```text
[HKLM\Software\Microsoft\FontLink\SystemLink]
Zegoe UI          = \Hard Disk\Fonts\ZuneCJK_UI_20261027.ttf,Zune UI CJK
Zegoe UI Light    = \Hard Disk\Fonts\ZuneCJK_UI_20261027.ttf,Zune UI CJK
Zegoe UI Semibold = \Hard Disk\Fonts\ZuneCJK_UI_20261027.ttf,Zune UI CJK
```

如果自行准备的字体字族不同，要替换右侧字族，而不是随意改系统原有的左侧字体名称。
加载器必须放在注册表指定的位置。位于 Windows 的 ROM 内置版本是另一种封装方式，
不能只改启动路径而不提供对应文件。

先从自己的系统镜像提取并解压 `default.fdf`，再离线生成中间配置：

```powershell
python tools/prepare_registry.py local-inputs/default.fdf generated/default.CJK.fdf --family "Zune UI CJK"
```

工具会保留无关配置，拒绝占用其他程序的 `Launch45`，并检查整个 `Init` 依赖图。
**输出仍是未压缩的注册表文件，不是固件。**

本项目修正过一次实际启动死锁：`Depend45` 等待 60，同时 `Depend60` 又等待 45。
不能把加载器“进入函数后会立即 SignalStarted”当作解除环的理由，因为它尚未获准启动。

## 6. 固件封装与安装边界

系统会从镜像加载默认注册表，不能靠一次性的 RAM 修改或不受支持的 `RegFlushKey` 达到本项目的持久化目标。

实际封装还必须处理：

1. 注册表重新压缩及解压后的逐字节一致性。
2. ROM 文件表、指针、物理范围及固定 RAM 起点之间的空间。
3. CE BIN 记录长度、地址、校验和与入口点。
4. 本机启动器实际采用的镜像接受策略与启动交接模式。
5. 目标文件的正确接收路径、完整传输及实际安装结果。
6. 安装失败后原机恢复镜像的完整写回。

仅有“权限很高”“TEST 模式”或“关闭签名检查”都不能代替上述检查。
部分改动曾导致进度条后黑屏；原机恢复成功后才继续定位。
本公开版没有省略这些边界并伪装成通用刷机脚本。

## 7. 真机验收

安装经过逐机核对的完整方案后：

1. 等待所有文件传输完成，回到正常主菜单。
2. 真实重启设备，不进入 Games、Connect 或手动字体程序。
3. 打开原生“音乐”，检查之前为方框的中文歌名。
4. 再次重启重复检查，并记录是否实际回到菜单。
5. 如同时验证 FLAC，使用短的自制音频，确认库时长、声音和重启保留。

“程序启动响应”“字体在进程中能画字”和“USB 重新出现”都不等于重启后的原生中文显示已经成功。
菜单仍是英文是当前预期行为。

## 8. MTP 和 FLAC 的关系

标准 MTP 允许 Windows 资源管理器显示 `Storage/Music`，并不提供普通 U 盘盘符。
普通文件复制、音乐库登记、FLAC 解码和专辑封面是不同环节。

Windows Shell 的普通复制会传入可识别的时长等属性。
本项目一个低层 WPD 测试工具漏传时长，产生了 0 秒条目；换成实际 Shell 复制后，新条目自动是 3 秒。
这不是把源 FLAC 改成其他格式，也不是已实现了所有拖入工具的自动时长修复。
