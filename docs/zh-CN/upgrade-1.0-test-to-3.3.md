# Zune 30G：从 1.0 TEST 到 3.3 的研究流程与新手说明

[English](../en/upgrade-1.0-test-to-3.3.md) · [技术解析与源码](../upgrade-internals.md) · [返回首页](../../README.md)

**想先用图形界面？请看 [Windows 升级助手使用说明](assistant.md)。**
新助手是限定已分析构建的实验 Alpha，已通过离线测试和打包自检，尚未完成真机全过程验收。
下面继续保留底层研究步骤，方便理解它做了什么。

## 先看结论：这个仓库现在能帮你做什么

我们在一台原先运行 `1.0 (186) TEST` 的 Zune 30G 上，实际做到了：

- 启动到 3.3，进入正常主菜单，“关于”显示 3.3。
- 在前一阶段用户真实重启后，仍能进入 3.3。
- 进一步修复兼容问题后，电脑的官方 Zune 软件出现设备图标。
- 后续在这台机器上继续安装了中文与 FLAC 适配版。

**最后用于修复电脑识别的 AUTH196 是基于官方 3.3 的定制研究镜像。它不是完全不改动的微软原版镜像。**
它在每次启动期间处理本机旧安全数据的兼容性，没有完成全部安全字段的永久迁移。
较早的“重启后 3.3 正常”和较后的“官方软件识别正常”来自不同验证阶段，不能合并成
“完全原版 3.3 所有功能和冷启动都已最终验收”。

这次公开的内容包括详细过程、实际 ARM 兼容代码、离线构建程序、备份校验程序和回归测试。
构建程序已经在维护者本地用同一批私有输入复现出与历史 AUTH196 **逐字节相同**的镜像。

**它还不是新手插上任意 Zune 就能运行的一键升级工具。**
普通 USB 文件夹读不到本流程需要的完整系统和安全区；新图形助手提供限定范围的实验实现，
仍不是通用 USB 备份器、安装器或恢复刷写器。第 5 步结束只代表在电脑上生成了文件。
第 6 步是历史安装流程的解释，需要针对设备核对传输程序，不能靠改文件扩展名或拖进 Music 完成。

## 1. 几个词先弄明白

| 名称 | 可以怎么理解 |
| --- | --- |
| 固件 / 系统镜像 | Zune 开机时加载的系统文件；这里主要讨论 `NK`。 |
| `NK.bin` | Windows CE 系统的容器文件，里面有程序、驱动、默认注册表等。不是普通音乐文件。 |
| 启动器 / EBoot | 系统之前运行的小程序，决定从哪里启动、怎样接收或检查镜像。 |
| TEST | 开发或测试配置；显示 TEST 不代表所有机器的程序、密钥和启动策略相同。 |
| NOR / 闪存 | 保存启动器、配置和部分安全数据的芯片区域。与电脑可见的 Music 文件夹不同。 |
| 安全区 / vault | 含设备身份、证书和加密字段的数据。每台机器必须用自己的。 |
| RAM 兼容处理 | 本次开机在内存里转换数据；断电后内存消失，下次启动重新执行。 |
| 持久化 | 改动能在重启后继续生效。每次开机自动执行内存处理，也可让功能持续生效，但不等于永久改写安全区。 |
| 哈希 / SHA-256 | 文件的校验指纹。用于检查备份、源文件和构建输出是否一致。 |
| MTP | Windows 显示便携设备文件夹的传输方式；不等于带盘符的 U 盘。 |

## 2. 适用范围和准备工作

本流程针对**第一代 Zune 30G**的特定 1.0 TEST 兼容问题。
不要套用到 Zune HD、80G、120G 或小容量闪存型号。

你需要准备：

1. Windows 电脑、可靠 USB 线，设备有足够电量。
2. Python；在终端执行 `python --version`，能看到版本号。
3. 本仓库：仓库首页点 **Code → Download ZIP**，解压到一个方便找到的文件夹。
4. 自己合法取得的、与下方指纹完全一致的 3.30.39 原始 NK。
5. **这台机器自己的**原系统、完整 NOR、硬盘前部以及旧安全区备份。
6. 已为这台机器实际确认的恢复方法和写回程序。

固件版本显示正确、能出现黄色菜单、或者手里有转接器，都不能单独证明恢复已经可用。
研究中我们实际写回过原机 1.0，并确认进入主菜单，之后才继续试验。
如果你只有音乐备份，没有下面的原机资料，先不要进入安装阶段。

## 3. 先保留原机备份

建议把下列文件放在仓库外的私有位置，再额外复制一份到另一块磁盘：

```text
自己的私有备份目录/
  nk.original.bin          原机当前可用的系统
  nor.original.bin         本研究布局中的完整 2 MiB NOR
  disk-prefix.original.bin 至少前 1 MiB、按 512 字节扇区对齐的硬盘备份
  vault.legacy.bin         原始 NOR 中 0x70000～0x7FFFF 的 64 KiB 旧数据
```

这里描述的是**已经读取出来的备份**。下面的脚本只检查它们，不会从 Zune 提取备份。
不要用本仓库的示例名称去建立空文件充数，也不要拿别人机器的同名文件代替。
USB 文件夹能拖歌，并不意味着能直接复制这些区域。

先打开解压后的仓库文件夹，确认里面能看到 `README.md` 和 `tools`。
在资源管理器顶部地址栏输入 `powershell`，按回车，就能在这个文件夹打开终端。
执行下面这一整行命令；把路径换成自己的实际位置：

```powershell
python tools/upgrade/check_backups.py --original-nk "local-inputs/nk.original.bin" --nor "local-inputs/nor.original.bin" --disk-prefix "local-inputs/disk-prefix.original.bin" --legacy-vault "local-inputs/vault.legacy.bin" --output "generated/backup-inventory.PRIVATE.json"
```

成功时会打印 JSON，其中包括：

```json
{
  "nk_record_checksums_valid": true,
  "vault_matches_original_nor_region": true,
  "backup_created_by_this_tool": false,
  "physical_recovery_tested_by_this_tool": false
}
```

每个文件还有 `bytes` 和 `sha256`。保存这份清单，并独立确认这些文件确实来自眼前这台机器。
文件之间匹配只能证明内容一致，不能自动证明机器身份。

如果提示 `Legacy vault does not match`，说明你选的安全区和原始 NOR 不一致；
先核对文件来源。**不要为通过检查而修改校验脚本或把当前区域冒充原始备份。**

## 4. 为什么直接刷 3.3 会黑屏

本机研究发现有两个不同层次的问题：

1. **启动阶段的数据校验不兼容。** 旧 TEST 数据与 3.3 使用的校验上下文、加密路径不相同。
2. **启动后电脑连接仍不正常。** 只处理最前面的 32 字节头部，可以让外层完整性检查通过，
   却不代表里面的私钥等字段已经按新路径正确解码。

所以“关于显示 3.3”不是所有问题都解决了。后来还需要验证认证挑战、受保护的文件枚举，
以及官方软件是否真的显示设备。

最终可工作的研究方案把**本机自己的旧加密数据**作为私有 ROM 文件保存，在系统读取时：

1. 校验输入大小和摘要。
2. 保存进来时的内存数据，用于出错回退。
3. 按已分析的 38 个字段范围进行旧格式解密、新路径加密与回读比较。
4. 重算对应头部的完整性信息，让原 3.3 逻辑再做检查。
5. 发生已处理的错误就恢复进来时的内存数据。

这个方案不需要把另一个人的私钥给你的机器，也没有在这一步永久写入完整新安全区。
技术细节和实际代码见 [源码解析](../upgrade-internals.md)。

## 5. 在电脑上构建私有研究镜像

### 5.1 安装依赖

在仓库根目录执行：

```powershell
python -m pip install -r requirements.txt
```

构建还需要 Windows 自带 `makecab.exe`，以及独立的 CE LZX 解压模块
`wincedecompr.py`。后者用于检查压缩结果确实能还原成输入数据。
从 [KodaSec/wince-decompr](https://github.com/KodaSec/wince-decompr) 点击 **Code → Download ZIP**，
解压后把 `wincedecompr.py` 放在 `local-inputs/ce-decoder/`，同时保留它自己的许可文件。
本次核对的脚本 SHA-256 为：

```text
42693ba5e756f664d2405bdaa2f6f9bc5671b5956439aeed581c8e7e89f2e72d
```

把这个模块目录传给 `--decompressor-dir`；支持目录中直接有这个文件，
或存在 `wince_decompr/wincedecompr.py` 的布局。
详见 [依赖说明](../../THIRD_PARTY_NOTICES.md)。本仓库没有打包微软固件或第三方解压器。

### 5.2 准备构建输入

```text
local-inputs/
  nk.stock33.bin       自己取得的原始 3.30.39 NK
  vault.legacy.bin     自己机器的 65536 字节原始旧安全区
```

本构建器支持的原始 NK 的 SHA-256 为：

```text
81951eaf10feb868e2f2818aea64d15f0b2b6484458454c2655efd0668c13a11
```

可以在 PowerShell 检查：

```powershell
Get-FileHash -Algorithm SHA256 "local-inputs/nk.stock33.bin"
Get-FileHash -Algorithm SHA256 "local-inputs/vault.legacy.bin"
```

只复制输出中 `Hash` 栏的 64 位十六进制字符，不要把整行路径一起复制。
第一项必须和上面的固定值一致。第二项要和**自己第 3 步的原始备份清单**一致；
每台设备的安全区摘要可以不同，不要复制维护者或其他网友的摘要。

### 5.3 执行构建

把 `自己的旧安全区SHA256` 替换成上一节得到的 64 位十六进制值，
把解压器目录改成自己的路径。`generated/auth196-local` 必须是尚不存在的新目录。

```powershell
python tools/upgrade/build_upgrade.py --stock-nk "local-inputs/nk.stock33.bin" --legacy-vault "local-inputs/vault.legacy.bin" --vault-sha256 "自己的旧安全区SHA256" --decompressor-dir "local-inputs/ce-decoder" --output-dir "generated/auth196-local"
```

成功后产生：

```text
generated/auth196-local/
  nk.AUTH196.PRIVATE.bin  本机私有研究镜像，含本机加密身份数据
  runtime.PRIVATE.bin     本次组装的 ARM 兼容例程
  build.PRIVATE.json      文件校验与布局检查结果
```

检查报告应有：

```json
{
  "rom_legacy_file_roundtrip_verified": true,
  "runtime_module_overlap": false,
  "persistent_security_write_implemented": false,
  "device_operations_performed": false,
  "new_device_hardware_boot_verified": false,
  "contains_owner_specific_encrypted_identity_material": true,
  "publish_generated_output": false
}
```

**`device_operations_performed: false` 的意思是：程序只在电脑上构建，没有给 Zune 刷机。**
生成成功也不表示你这台机器已经适配成功。
默认随机生成日志标识，所以不同次输出的镜像哈希通常不同。
`--journal-token` 只用于维护者在本地复现历史输入，不是密码或刷机验证码。

### 5.4 遇到错误怎么办

| 提示 | 原因和处理 |
| --- | --- |
| `Stock NK SHA256 mismatch` | 原始系统文件不是本工具核对过的版本；不要改常量强行构建。 |
| `Local legacy backup size/hash mismatch` | 大小不对、路径选错或摘要抄错；回到原始清单核对。 |
| 找不到 `wincedecompr.py` | `--decompressor-dir` 没指向正确目录。 |
| `MakeCAB failed` | 检查 `makecab.exe` 路径、临时目录空间和 Windows 环境。 |
| `Output folder exists` | 为本次构建换一个新的输出目录；程序不会覆盖旧结果。 |
| `ROM ... overlaps ...` / `Unexpected ...` | 布局或原始程序不符合预期；停在电脑端调查，不安装。 |

## 6. 真机安装：历史上怎样完成，公开版还缺什么

**本节是已成功机器的安装过程说明，不是可以直接执行的通用 USB 刷机命令。**
本仓库的 `app/` 现有实验 WPD 后端及完整受限状态机，使用要求见 [助手说明](assistant.md)。
它尚未通过新工具真机验收；不能把这段底层说明当作“只差运行一个命令”。
普通读者如果没有对应的备份/恢复和安装程序，请停在离线构建阶段。

成功试验的程序依次执行：

1. 读取设备身份，确认仍是同一台原先备份的机器，且固件状态符合预期。
2. 确认已有恢复记录、原系统哈希、NOR 和硬盘前部备份都匹配。
3. 检查固件接收队列为空，避免把不明的待安装文件一并提交。
4. 使用设备实际支持的特殊固件对象格式 `0xB802`，暂存名为 `nk.bin` 的镜像。
5. 在当时正常 1.0 接口中，完整分段回读暂存镜像并核对每一字节和 SHA-256。
6. 再次确认待提交的只有刚验证的对象，**发送一次**安装提交。
7. 观察启动结果。USB 在重启时断开不等于安装失败，也不能因此重复提交。

技术读者可以在 [安装状态机说明](../upgrade-internals.md#usb-transfer-and-commit) 查看协议顺序。
恢复模式的读回能力与正常模式不同；历史上恢复接口不支持完整暂存回读。
所以“传输已收到确认”和“完整文件已回读验证”必须分别记录。

本轮发布只构建和整理资料，没有再次操作维护者的 Zune。

## 7. 如何判断升级真的成功

把这些结果逐项记录，不要只拍一张版本号：

| 检查 | 成功表现 |
| --- | --- |
| 首次启动 | 进入音乐／视频等正常主菜单，不是进度条后一直黑屏。 |
| 版本 | “设置 → 关于”显示 3.3；USB 版本信息与之相符。 |
| 重启 | 重新启动后仍能进入菜单；记录测试的是哪个具体镜像。 |
| 官方软件 | 打开电脑 Zune 软件，确实出现这台设备的图标。 |
| 内容与稳定性 | 分别检查库、播放、同步、长时间待机；未做的项目不要记为通过。 |

研究中使用通用公开测试证书时曾收到 `0x2020`，而使用本机身份完成的挑战验证通过。
因此不能只凭一次认证被拒绝就断言系统没启动或 RSA 数据一定损坏。
官方软件识别、协议挑战通过和长期稳定运行仍是不同检查。

## 8. 黑屏或循环重启时怎样处理

下面按键路径在本项目的 TEST 启动器机器上成功过，不能保证每台 Zune 都一样。
先保持供电，确认顶部 HOLD 已解锁。

1. 按住左侧“返回”，短按一次“播放”后立即松开播放，继续按返回约 20 秒。
2. 出现黄色 **Pyxis maintenance** 后松开所有按键。
3. 在黄色维护画面**只短按一次返回**，进入屏幕提示连接电脑恢复固件的画面。
4. 使用已经为本机核对过的恢复工具，只写回这台机器原先可正常启动的 NK。
5. 回到主菜单后核对身份、系统版本和原文件哈希，再决定下一次试验。

如果设备状态允许，也曾用“返回＋向上”触发重启，并在松开向上后保留返回进入黄色画面。
如果始终进不了维护入口，不要反复尝试格式化或改变启动配置来碰运气。

**不要选择 `restore factory defaults`、`format data partition` 或 `initialize disk`。**
它们分别是恢复出厂、格式化数据分区、初始化磁盘，与“通过 USB 写回已备份 NK”不是一回事。
研究中关闭并保存 SIG 也曾造成黑屏；本 AUTH196 构建流程不要求修改启动器、SIG 或分区。

电脑上的 Zune 软件可能自动占用 USB。如果它在安装或同步，先等结束；没有传输时再退出，
由对应恢复程序接管。显示“连接电脑恢复”也不等于必须依赖在线服务器；本项目使用过本地镜像恢复，
实验助手仅提供已分析接口的引导恢复，并非通用恢复工具。

## 9. 哪些文件能分享

- 可以分享：仓库网址、教程、原创源码、离线测试结果。
- 只留自己：原机备份、安全区、私钥、构建输出、私有构建报告和认证日志。
- `nk.AUTH196.PRIVATE.bin` 即使只包含加密数据，也带有你机器的身份材料，不作为公共固件分享。
- `.gitignore` 只帮助 Git 忽略文件；网页手动上传仍可能把私有文件发出去。

## 10. 下一步研究方向

目前可用路线是“3.3 派生镜像＋每次启动的本机 RAM 兼容处理”。
完全不修改 3.3 且永久兼容全部安全字段、通用的 USB 原机备份/恢复/安装程序，
仍需要进一步研究、逐机验证和文档化。
本文把已经完成和仍缺少的环节分开，供后来者从实际代码继续，而不是再次从黑屏猜起。
